**Audit Date:** October 23, 2026  
**Auditor:** Senior Software Architect, Full-Stack QA Engineer, and Application Security Specialist  
**Target Application:** TripPilot AI (FastAPI Backend + React/Vite/Tailwind Frontend + Supabase PostgreSQL + Razorpay Gateway + Groq Cloud AI)  
**Status:** Complete Audit — Read-Only — Awaiting Approval Before Implementing Changes

## 1. Executive Summary

A comprehensive, end-to-end read-only audit of the **TripPilot AI** multimodal travel booking platform was conducted across the user interface, state management, API contracts, business logic, persistence layer, AI integration, payment processing, security posture, and automated test coverage.

### Key Audit Findings
1. **Frontend-to-Backend State & Filter Desynchronization:** Departure time window filtering (`time_of_day`), selected travel dates, and mode-specific parameters (train classes, airlines, bus operators) are completely dropped or ignored between UI components, the API client, and backend services.
2. **Date/Time Arithmetic & Multimodal Connection Defects:** Connection buffer and total travel duration calculations discard calendar date components, causing impossible past transfers to be treated as valid 22-hour buffers, multi-day journeys to be calculated within a 24-hour window, and overnight journeys in seed data to have arrival timestamps earlier on the same calendar day than departure times.
3. **AI Assistant Multi-Turn Context Loss & Navigation Gaps:** The conversational assistant loses message history across turns because `conversation_history` is never transmitted by the store or processed by the backend. Furthermore, search action proposals generated by the AI update state silently without navigating users to `/explore`, and the `open_login` action proposal is unhandled by the frontend store.
4. **Persistence & Booking Mutation Gaps:** The `PATCH /api/bookings/{booking_id}` endpoint updates in-memory dictionaries but never writes to Supabase. Supabase booking lookups by reference number (`TP-XXXXXX`) fail because the query only checks the `id` column. Composed multimodal itineraries exist only in an ephemeral in-memory dictionary and expire on backend restarts.
5. **Security & RLS Permissiveness:** Overly permissive Supabase Row Level Security (`USING (true)`) allows direct public extraction of all user accounts (including password hashes) and bookings via the PostgREST API using the public anonymous key. JWT tokens remain stored in browser `localStorage`.
6. **Automated Testing Vacuum:** The backend has 0 automated tests (`pytest` collects 0 items). The frontend has only 3 files containing 10 mock tests that assert inline mathematical operations without exercising any actual store, service, or component code.

#### INT-04: Connection Buffer and Total Duration Calculations Discard Calendar Dates
- **Severity:** 🔴 Critical
- **Status:** Confirmed Defect
- **Affected Files:**
  - [`backend/app/services/multimodal_service.py:L21-57`](file:///e:/Vibe_Code_Projects/AI%20Powered%20Travel%20Site/backend/app/services/multimodal_service.py#L21-L57)
  - [`backend/app/services/multimodal_service.py:L98-103`](file:///e:/Vibe_Code_Projects/AI%20Powered%20Travel%20Site/backend/app/services/multimodal_service.py#L98-L103)
- **Evidence:**
  ```python
  @staticmethod
  def parse_time_minutes(time_str: str) -> int:
      if "T" in time_str:
          time_part = time_str.split("T")[1]
      else:
          time_part = time_str
      parts = time_part.split(":")
      return int(parts[0]) * 60 + int(parts[1])
  ```
  ```python
  buffer_minutes = dep_m - arr_m
  if buffer_minutes < 0:
      buffer_minutes += 24 * 60

  if buffer_minutes < 0: # Line 51: Unreachable dead code!
      return (False, buffer_minutes, "Impossible connection: Leg departs before previous leg arrives.")
  ```
- **Reproduction Steps:**
  1. Construct a multimodal journey with Leg 1 arriving at `2026-10-25T23:30:00` and Leg 2 departing on the *previous* calendar day at `2026-10-24T06:00:00`.
  2. Call `MultimodalService.validate_connection(leg_a, leg_b)`.
  3. `dep_m - arr_m = 360 - 1410 = -1050`. Because it adds `1440`, `buffer_minutes` becomes `+390` minutes.
  4. The impossible chronological connection returns `(True, 390, 'Comfortable transfer buffer: 390m available.')`.
  5. Furthermore, in `compose_multimodal_journey` lines 98–103, for any multi-day journey (e.g. 32 hours), `total_duration = end_m - start_m` modulo 24 hours computes duration as 8 hours instead of 32 hours.
- **Expected Behaviour:** Timestamps should be parsed using `datetime.fromisoformat()` with full calendar date comparison. If Leg B departs before Leg A in absolute time, `buffer_minutes < 0` must return `is_valid: False`. Total journey duration should reflect exact elapsed minutes `(end_dt - start_dt).total_seconds() / 60`.
- **Actual Behaviour:** Only hours and minutes from midnight are evaluated. Impossible backwards connections are accepted, and line 51 is dead code.
- **Proposed Fix:** Replace `parse_time_minutes` with ISO datetime parsing:
  ```python
  dep_dt = datetime.fromisoformat(leg_b["departure_time"])
  arr_dt = datetime.fromisoformat(leg_a["arrival_time"])
  buffer_minutes = int((dep_dt - arr_dt).total_seconds() / 60)
  if buffer_minutes < 0:
      return (False, buffer_minutes, "Impossible connection: Leg departs before previous leg arrives.")
  ```

#### INT-17: Permissive Supabase Row Level Security (RLS) Exposes Users and Bookings Publicly
- **Severity:** 🔴 Critical
- **Status:** Confirmed Vulnerability
- **Affected Files:**
  - [`backend/schema.sql:L147-164`](file:///e:/Vibe_Code_Projects/AI%20Powered%20Travel%20Site/backend/schema.sql#L147-L164)
- **Evidence:**
  ```sql
  CREATE POLICY "Allow public read on bookings" ON public.bookings FOR SELECT USING (true);
  CREATE POLICY "Allow public insert on bookings" ON public.bookings FOR INSERT WITH CHECK (true);
  CREATE POLICY "Allow public update on bookings" ON public.bookings FOR UPDATE USING (true);

  CREATE POLICY "Allow public insert on users" ON public.users FOR INSERT WITH CHECK (true);
  CREATE POLICY "Allow public select on users" ON public.users FOR SELECT USING (true);
  ```
- **Reproduction Steps:**
  1. Send a GET request to the Supabase PostgREST endpoint using the public `anon` key:
     `curl -H "apikey: <SUPABASE_ANON_KEY>" https://<project-ref>.supabase.co/rest/v1/users?select=*`
  2. The endpoint returns all registered users including `password_hash`, `email`, `phone`, and `name`.
  3. Send `curl -H "apikey: <SUPABASE_ANON_KEY>" https://<project-ref>.supabase.co/rest/v1/bookings?select=*`
  4. The endpoint returns all customer bookings, passenger details, contact emails, and trip itineraries without authentication.
- **Expected Behaviour:** Direct client PostgREST access to `users` and `bookings` tables should be disabled or restricted to `service_role` only, or scoped using `auth.uid() = user_id`.
- **Actual Behaviour:** Any party with the anonymous key can read, insert, and update all user and booking records directly from Supabase, bypassing FastAPI application controls.
- **Proposed Fix:** In `schema.sql`:
  1. Revoke public SELECT on `users` table:
     ```sql
     DROP POLICY IF EXISTS "Allow public select on users" ON public.users;
     CREATE POLICY "Disallow public select on users" ON public.users FOR SELECT USING (false);
     ```
  2. For `bookings`, restrict SELECT and UPDATE to authenticated user ownership:
     ```sql
     DROP POLICY IF EXISTS "Allow public read on bookings" ON public.bookings;
     CREATE POLICY "User bookings select" ON public.bookings FOR SELECT 
       USING (auth.uid()::text = user_id OR contact_email = auth.jwt()->>'email');
     ```

  `r"^https://ai[-_]trip[-_]planner(-[a-zA-Z0-9_\-]+)?-hariprathap1804's-projects\.vercel\.app$"` or validate against specific Vercel team slugs.

#### SUS-02: Unbounded Memory Growth in Module-Level IP Rate Limiter Maps
- **Severity:** 🟢 Low
- **Status:** Suspected Issue
- **Affected Files:**
  - [`backend/app/routers/ai.py:L14`](file:///e:/Vibe_Code_Projects/AI%20Powered%20Travel%20Site/backend/app/routers/ai.py#L14)
  - [`backend/app/routers/auth.py:L45`](file:///e:/Vibe_Code_Projects/AI%20Powered%20Travel%20Site/backend/app/routers/auth.py#L45)
- **Evidence:**
  `_ai_rate_limits = defaultdict(list)` and `_auth_rate_limits = defaultdict(list)` maintain timestamps per IP. While old timestamps within each list are pruned on access, dictionary keys for inactive IPs are never evicted. Over long server runtimes with millions of distinct IPs, the dictionaries grow monotonically.
- **Proposed Fix:** Implement periodic pruning or use a bounded TTL cache (`cachetools.TTLCache(maxsize=10000, ttl=300)`).
